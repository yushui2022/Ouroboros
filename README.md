# Ouroboros

给自进化 Agent 装一个**可拨动的方向控制面**。

> 一句话：现在的自进化系统只告诉你"总分涨了"；我们要让它告诉你"往哪走、代价是什么、丢了什么"。

---

## 一、这个项目是什么

一个**可插拔的组件**，插到已有的自进化 Agent 上（DGM / ACE / GEPA / pi / dsh 等），提供三件事：

| 组件 | 管什么 | 回答的问题 |
| --- | --- | --- |
| **能力账本** | 层次 x 能力 | 我会什么？丢了什么？是哪次改动导致的？ |
| **方向控制** | 层次 x 指标 | 这一代往哪个指标使劲？代价是什么？ |
| **盲区出题** | 补覆盖空白 | 我该练什么？ |

**这个项目不是**：又一个自进化框架。循环、变异器、评测装置、容器编排全部由被测系统提供。我们只补它们缺的零件。

## 二、要解决的两个盲区

现在的自进化系统（DGM、GEPA、ACE 等）有两个结构性盲区。

**盲区一：只看得见总分。**

假设 Agent 从 30% 涨到 55%。中间发生了什么，没人知道。真实情况很可能是"学会了 5 类新题，同时悄悄丢了 3 类老题"——因为 55 > 30，所以没人发现。

后果：

1. 它会偷偷变傻，而你查不出是从哪一代开始丢的、为什么丢
2. 分数掉了，你分不清这是"有价值的探索性退步"还是"真的退化"——两者在总分上长得一模一样
3. 它在走回头路：每代让模型想"该改什么"时都是从零开始，不知道前面试过什么

**盲区二：只能朝一个方向。**

现在的系统只会说"让它更强"。用户没法说"我要省 40% 的 token，最多接受掉 3% 准确率"，也看不到这个选择的代价。

## 三、核心设计

### 3.1 两个正交的轴

这两件事经常被混为一谈，必须分开：

- **层次** = 改**哪里**（指令 / 上下文 / 工具 / 编排 / 代码 / 权重 / 评测）
- **指标** = 往**哪个方向**使劲（准确率 / token / 延迟 / ...）

**层次 x 指标 = 真正的搜索空间。**

### 3.2 指标分三层

不是"保留几个指标"，而是分三层，每层处理方式完全不同：

| 层 | 数量 | 参不参与权衡 | 例子 |
| --- | --- | --- | --- |
| **底线** | 不限 | 不参与。二值：过 / 不过 | 历史能力保留、越界行为必须为 0 |
| **主旋钮** | **1~3 个** | 参与。这就是帕累托前沿的轴 | 准确率、token |
| **观测项** | 不限 | 不参与，只记录 | 延迟、步数、工具错误率 |

**主旋钮最多 3 个**，理由是数学的：维度越高，帕累托前沿上的点越多。2 维时 10 个版本可能只剩 3 个没被碾压；5 维时可能 9 个都没被碾压——筛选等于失效。

### 3.3 帕累托前沿就是用户界面

不要求"又准又省"——那不可能。正确做法是维护**帕累托前沿**（没有被别的版本全面碾压的那些版本），把它摆给用户挑：

```
准确率
  85% |                    E
  82% |            A
  79% |        B
  75% |    C
       +---------------------------> token
         8k    18k   30k   45k
```

选哪个取决于你要什么，没有哪个是"最优"。用户拨动，系统朝那个方向搜。

**绝对不要用加权求和**（"准确率 x 0.7 + 速度 x 0.3"）——那个权重没法定，定错了整个系统会朝一个奇怪的方向狂奔。

### 3.4 底线不可拨，旋钮可拨

- **旋钮（可拨）**：准确率 / token / 延迟 —— 这些是权衡，用户有权选
- **底线（不可拨）**：已经学会的能力、安全性 —— 不许被牺牲，哪怕用户要求

**账本在这里的角色就是守底线**：它知道"第 17 项能力曾经会过"，任何为省钱把它弄丢的版本都会被拦下或标记。

> 没有底线，"自由控制方向"就是自由地把它调废。

## 四、执行顺序

顺序不能反：

```
账本（状态） -> 方向控制（策略） -> 盲区出题（生成器）
                        |
              固定 held-out 判收不收
```

**反过来必崩**：没有账本，方向控制就是瞎指挥；没有可靠的状态，出题器只会重复生产已有的题。

## 五、路线图

| 阶段 | 做什么 | 验收标准 |
| --- | --- | --- |
| **0** | 建测量装置：冻结模型 + 冻结任务集 + 固定预算，先复现基线 | 能重复跑出一致的数字，而不是"感觉差不多" |
| **1** | 能力账本：能力表 + 父代/子代差分 + 因果链 | 能回答"第 N 项能力是第几代丢的、哪次改动导致的" |
| **2** | 方向控制：多指标记录 + 帕累托前沿 + 用户选择 | 能画出一张前沿图，用户拨动后系统改变搜索方向 |
| **3** | 跨代信用分配：把历史喂回变异器 | 同等预算下，收敛速度优于不带账本的基线 |
| **4** | 盲区出题 + 环外审计 | 自生成题目能覆盖未测能力，且 held-out 指标不被自欺污染 |

### 第一周的最小实现

- 2 个指标：准确率 + token
- 每个版本记这 2 个数
- 接受准则：只留没被全面碾压的版本
- 一张二维图
- 用户挑一个点当目标

跑通"1 代闭环"比做精美的 archive 重要得多。

## 七、真实风险

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **奖励黑客** | 系统学会骗评委：硬编码答案、改测试、探测评测环境 | 评测集只读挂载；接受前用全新任务复测；静态扫描 genomic 里的可疑模式 |
| **过拟合** | 分数涨在训练集上 | held-out 物理隔离，永不进环；周期性换新题 |
| **多目标失效** | 主旋钮超过 3 个，前沿退化成"几乎全部" | 严格限制主旋钮数量 |
| **自欺出题** | 自己出题自己判 -> 越打越高 | 出题可自生，**判定必须外部锚定** |
| **成本** | 每代都是 N 次评测 x 任务数 | 主指标每次测，次要指标按需测 |
| **收益递减** | 几代后停滞是常态 | 设代数 / 成本 / 边际收益三个停止条件 |

## 八、已核实的关键结论

以下结论经过实际核查（2026-09-15），不是凭印象：

1. **DGM 的接受准则不是棘轮，是地板。** `DGM_outer.py` 里 `score >= 初始分 - 0.1`——意思是"别比初代差 10% 以上"。从 50% 掉到 21% 的后代（初代 30%）照样进档，没有任何单调性保证。
2. **DGM 的存档只用一个聚合分数做决策。** per-instance 的 resolved / unresolved id 列表存了，但选择父代（`choose_selfimproves`）和接受（`update_archive`）都只看 `accuracy_score`。所以它问不出"这一代具体多了哪几项、少了哪几项"。
3. **DGM 的整个自改进循环在 LLM 层面是无状态的。** `self_improve_step.py` 两处调用 `msg_history=None`，`coding_agent.py` 三处 `msg_history=[]`。每代都是从零推导改进方向——相当于 SGD 但批次为 1、没有动量、每步随机重新初始化。
4. **"防退化门控"在工程侧已经拥挤**：Tracely-ai 1408 stars、agent-qa 909 stars。但它们全是给人类开发者的 CI 工具（守人工变更），不是进化循环内的选择压力。
5. **"自生成 benchmark"在工程侧接近空白**：搜到的只有 Absolute Zero 复现（1 star）和几个 0 star 项目。空间比门控那块开放得多。
6. **论文线缺记忆，产品线记忆是主流，两边互不引用。** 扫了 9 个自进化仓库，Letta / Mem0 / Zep / TencentDB-Agent-Memory 零命中；而产品侧 MemOS 11k、OpenViking 37k、EverOS 13k、Letta 25k、TencentDB-Agent-Memory 27k 全在打 "self-evolving memory" 这个词。
