# Ouroboros 设计文档

本文档记录完整设计。README 是入口，这里是细节。

---

## 1. 两个正交的轴

讨论自进化时最容易混淆的两件事：

- **层次** = 改**哪里**
- **指标（方向）** = 往**哪个方向**使劲

它们垂直。同一个层次可以往不同方向调；同一个方向可以用不同层次实现。

```
                准确率    token    延迟
  指令层           x         x
  上下文层         x         x
  工具层           x
  编排层           x                   x
  代码层           x                   x
  权重层           x                   x
```

**层次 x 指标 = 真正的搜索空间。** 横轴是"可调旋钮的位置"，竖轴是"想要什么效果"。

## 2. 进化层次：6 + 1

| # | 改什么 | 代表工作 |
| --- | --- | --- |
| 1 | **指令层** — 提示词、系统提示 | APE / OPRO / ProTeGi / TextGrad / GEPA |
| 2 | **上下文层** — playbook、记忆内容 | ACE |
| 3 | **工具层** — 工具箱本身（增删改工具） | Voyager 技能库 |
| 4 | **编排层** — workflow、子 agent 拓扑、规划策略 | ADAS、GPTSwarm |
| 5 | **代码层** — Agent 自己的源码 | DGM、SICA |
| 6 | **权重层** — 模型参数 | SEAL、STaR、RLVR |
| **+1** | **评测层** — 任务与判定标准本身 | Aspire、R-Zero、Absolute Zero |

前 6 个改的是"Agent 怎么做"，第 7 个改的是"**什么叫做好**"。第 7 个是唯一能称为颠覆的一层，风险也最高。

**本项目的定位在 1~5 层**（harness / 上下文层），因为权重层需要 GPU 微调，本机不具备条件。

## 3. 进化信号从哪来

与"改哪里"正交的另一个维度，按强弱排（越往下越危险，也越有想象空间）：

| 级别 | 信号来源 | 可靠性 |
| --- | --- | --- |
| 1 | 人类标注的测试集 | 最高，最常用 |
| 2 | 环境可执行反馈（编译 / 测试 / 游戏分数） | 最高，最干净 |
| 3 | 模型自我反思（Reflexion / GEPA） | 可用，会自欺 |
| 4 | 模型自出题自判 | 最容易崩 |
| 5 | 只给模糊目标 | 最接近真正闭合 |

**结论：只用 1 和 2 做主信号，3 只能辅助，4 和 5 需要额外的隔离设计才敢碰。**

## 4. 指标分三层

问题不是"保留几个指标"，而是分三层，每层处理方式完全不同。

| 层 | 数量 | 参不参与权衡 | 处理方式 |
| --- | --- | --- | --- |
| **底线** | 不限 | 不参与 | 二值门禁：过 / 不过，达不到直接拒绝 |
| **主旋钮** | **1~3 个** | 参与 | 帕累托前沿的轴 |
| **观测项** | 不限 | 不参与 | 只记录，用于事后分析和告警 |

### 4.1 为什么主旋钮最多 3 个

**理由一：测量成本。** 每个轴都要跑评测，3 个轴 = 每个版本测 3 次，钱和时间 x3。

**理由二：人类看得懂的上限。** 2 个指标能画二维图让用户挑点；3 个勉强（气泡大小当第三维）；4 个开始没人看得懂，必须降维成综合分数——而一旦降维，就退回了加权求和，"让用户自由控制方向"这件事就没了。

**理由三（硬道理）：帕累托前沿会失效。**

维度越高，前沿上的点越多：

| 维度 | 10 个版本中留在前沿上的数量 |
| --- | --- |
| 2 维 | 约 3 个 → 筛选有效 |
| 3 维 | 约 5~6 个 |
| 5 维 | 约 9 个 → **等于没筛** |

原因：在高维空间，"一个点被另一个点全面碾压"的概率急剧下降。所以主旋钮超过 3 个，整套方法在数学上就失效了。

## 5. 完整指标清单

### 质量类

| 指标 | 建议归属 | 说明 |
| --- | --- | --- |
| 任务通过率 / 准确率 | **主旋钮** | 几乎必选 |
| 输出正确性 | 并入准确率 | 有 ground truth 时 |
| 多次运行方差 | 观测项 | 衡量稳定性，不参与决策 |
| 泛化性 | 不是指标 | 是**验证方式**（用 held-out 测准确率） |

### 成本类

| 指标 | 建议归属 | 说明 |
| --- | --- | --- |
| Token 消耗 | **主旋钮** | 第二热门，建议选 |
| 金钱成本 | 观测项 | 与 token 高度相关，通常选一个 |
| 延迟 / 墙钟时间 | 观测项 | 测量贵，按需测；用户明确在意速度时才升为主旋钮 |
| 调用轮数 / 步数 | 观测项 | 与延迟高度相关 |

### 过程质量类

| 指标 | 建议归属 |
| --- | --- |
| 工具调用错误率 | 观测项 |
| 卡死 / 无效循环率 | 观测项 |
| 上下文压缩损失 | 观测项 |
| 上下文窗口占用峰值 | 观测项 |

### 底线类（不进旋钮）

| 指标 | 说明 |
| --- | --- |
| 历史能力保留率 | 账本管。曾经会的不许丢 |
| 越界行为：改测试 / 写系统目录 / 外联 | 必须为 0 |

### 产品类（做给用户用时）

| 指标 | 建议归属 |
| --- | --- |
| 用户干预次数 | 观测项 |
| 澄清提问次数 | 观测项 |

## 6. 判断某个指标该进哪一层

问三个问题，**三个全过才进主旋钮**：

1. 它**便宜、能每次都测**吗？
2. 用户**真的会为它做取舍**吗？（会为了它牺牲别的吗）
3. 它和已有的旋钮**独立**吗？（不高度相关）

任何一个不过 → 降级为观测项。

### 6.1 容易混淆的"假指标"

很多看起来不同的指标其实是同一个轴的不同测法，重复计入只会浪费维度预算：

| 看起来像新指标 | 实际是 |
| --- | --- |
| 泛化性 | 验证方式（用 held-out 测准确率） |
| 鲁棒性 | 同一指标多次运行的方差 |
| 金钱成本 vs token | 高度相关，选一个 |
| 步数 vs 延迟 | 高度相关 |

**真实的独立轴其实很少。** 很多人一上来列七八个指标，实际只有两个是独立的。

## 7. 帕累托前沿就是用户界面

### 7.1 定义

一个版本 A **支配**版本 B，当且仅当 A 在所有主旋钮上都不差于 B，且至少在一个上严格更好。被支配的版本直接扔掉。剩下的就是**帕累托前沿**。

### 7.2 例子

| 版本 | 准确率 | token | 命运 |
| --- | --- | --- | --- |
| A | 82% | 30k | 在前沿上 |
| B | 79% | 18k | 在前沿上 |
| C | 75% | 8k | 在前沿上 |
| D | 70% | 25k | **被 A 全面碾压 → 扔掉** |
| E | 85% | 45k | 在前沿上 |

```
准确率
  85% |                    E
  82% |            A
  79% |        B
  75% |    C
       +---------------------------> token
         8k    18k   30k   45k
```

前沿上的每个点都是**合法选择**，没有哪个是"最优"。选哪个取决于用户要什么。

### 7.3 为什么不用加权求和

`score = 准确率 x 0.7 + 速度 x 0.3` 这种做法的问题是：**权重你根本没法确定**。

- 权重定错，整个系统会朝一个奇怪的方向狂奔
- 权重是隐式的，用户看不见也改不了
- 不同任务需要不同权重，但权重是写死的

帕累托前沿把"权重"这个隐含假设**显式化**成交互：与其猜权重，不如把选项摆出来让用户挑。

## 8. 能力账本

### 8.1 它解决什么

回答三个问题：

1. 它现在**会做什么**（一项一项，不是一个百分比）
2. 每次改动后**多了哪几项、少了哪几项**
3. 少掉的那些**是哪一次改动导致的**

### 8.2 数据结构（草案）

```yaml
version: 47
parent: 43
timestamp: 2026-09-15T21:00:00+08:00

metrics:                      # 主旋钮，参与决策
  accuracy: 0.79
  tokens: 18000

observations:                 # 观测项，不参与决策
  latency_ms: 14000
  steps: 12
  tool_errors: 1
  context_peak: 0.71

capabilities:                 # 能力表，底线
  - id: cap-017
    name: 多文件重构
    status: pass
  - id: cap-018
    name: 并发 bug 定位
    status: fail              # 这一代丢了

edit:                         # 意图，用于因果归因
  layer: context              # 改的是哪一层
  summary: 压缩策略改为先摘要后丢弃
  diff_ref: patches/47.diff

delta:                        # 父代 -> 子代 差分
  gained: [cap-031, cap-032]
  lost: [cap-018]

attribution:                  # 因果链
  cap-018:
    lost_at: 47
    caused_by: context 层压缩策略改动
    recovered_at: null
```

### 8.3 三个关键字段

- `capabilities` —— 把 per-task 的通过/失败结果**归到具名能力**上。这是整个设计的核心，也是最难的一步：怎么定义"一项能力"、怎么判断"丢了"。
- `edit` —— 记录**意图**。没有它就无法做因果归属。DGM 缺的就是这个。
- `attribution` —— 把"哪次改动"和"丢了哪项能力"绑定，形成可查询的历史。

### 8.4 它与现有工作的区别

| 已有做法 | 它有什么 | 缺什么 |
| --- | --- | --- |
| CI 回归门控（Tracely-ai / agent-qa） | 二值门禁：套件过没过 | 没有能力粒度、没有跨代因果 |
| DGM 的 archive | 每个版本的聚合分数 + 谱系 | 只用一个标量决策，per-instance 结果存而不用 |
| GEPA 的帕累托 | 在**实例**维度上的帕累托 | 不在**指标**维度上 |

## 9. 方向控制器

### 9.1 它做什么

基于账本决定：**这一代替换哪一层、朝哪个指标、步子多大、约束是什么。**

这是账本的"行动侧"。账本是状态，控制器是策略。

### 9.2 为什么需要它

DGM 里"该改什么"由每一代的 o1 从零推导，而且只在代码层改。没有任何持久机制记住"上次往这个方向走代价是多少"。

有了控制器可以做到：

- 第 10 代攻工具层
- 第 11 代攻指令层
- 第 12 代回头补盲区

**这是现在的系统做不到的动作。**

### 9.3 一个必须回答的问题

> "往这个方向走，会削弱什么？"

这个问题只能从账本里回答——它需要**历史上往这个方向走时的代价数据**。这是账本真正发光的地方，也是它作为"代价度量表"的价值。

## 10. 盲区出题器

### 10.1 铁律：出题可自生，判定不能自生

如果系统既出题又判分，收敛结果必然是"自己给自己打高分"，越打越高，与真实能力脱钩。这是自进化的经典死法。

正确拆法：

| 用途 | 谁提供 |
| --- | --- |
| **练**（探索、发现盲区） | 可以自生成 |
| **判**（决定收不收） | 必须外部锚定，固定、物理隔离、人类验证过 |

### 10.2 自生成题目的真正价值是找盲区，不是打分

固定测试集必然有覆盖空白——有些能力你根本没有题去测。生成器的作用是**专攻这些空白**。

这两件事混起来就废了。

### 10.3 用可机械验证的筛子控制质量

好消息是"题目质量"不需要人来判断：

- 一道题如果当前 Agent 100% 通过或 0% 通过 → 没有信息量，扔掉
- 只有通过率在中间区间（例如 0.2~0.8）的题才有区分度

这个筛子不可作弊，完全自动。所以你不需要"判断题目好不好"，只需要"筛掉没有区分度的题"。

这一步把方案从"容易崩"拉回到"工程可做"。

## 11. 执行顺序

```
账本（状态） -> 方向控制（策略） -> 盲区出题（生成器）
                        |
              固定 held-out 判收不收
```

**顺序不能反，反过来必崩：**

- 没有账本，控制器就是瞎指挥
- 没有可靠的状态，出题器只会重复生产已有的题
- 没有底线，方向控制就是自由地把它调废

## 12. 验证方式

### 12.1 必须做对照实验

**同一个循环，带账本 vs 不带账本。** 这是唯一能证明它有用的方法。

这也是为什么本项目做**可插拔组件**而不是自己造 Agent——自己造整个 Agent 就无法归因"是账本的功劳还是别的地方写得好"。

### 12.2 测量协议

- **任务流**：isolated（每个任务独立）与 **sequential**（顺序流）两种
- **指标**：gain（增益）与 **forgetting / backward transfer**（保留与遗忘）
- 参考协议：Continual Learning Bench (2606.05661) 的显式 gain metric；AgentStream 的 isolated / sequential / interleaved 三模式

### 12.3 两种结果都有价值

- forgetting 显著下降且 gain 不降 → 机制成立
- gain 被压下去了 → **量化出了"单调性的代价"**，这本身就是一个干净的科学结论

### 12.4 域的选择

**选可执行验证的域**（代码 / 工具调用），不要选开放域。

理由：棘轮机制只在"回归可自动验证"的域里便宜——回归测试就是重跑一遍测试，成本近乎为零。开放域里这个优势会消失。

## 13. 真实风险

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **奖励黑客** | 硬编码答案、改测试、探测评测环境特征 | 评测集只读挂载；接受前用全新任务复测；静态扫描可疑模式；前期人工过目每个 diff |
| **过拟合** | 分数涨在训练集上 | held-out 物理隔离、永不进环；周期性换新题 |
| **多目标失效** | 主旋钮超过 3 个，前沿退化 | 严格限制主旋钮数量（见 4.1） |
| **自欺出题** | 自己出题自己判 | 出题 / 判定分离（见 10.1） |
| **能力定义困难** | "一项能力"怎么切分是主观的 | 前期用粗粒度，宁可少而准 |
| **成本** | 每代 N 次评测 x 任务数 | 主指标每次测，次要指标按需测 |
| **收益递减** | 几代后停滞是常态 | 设代数 / 成本 / 边际收益三个停止条件 |
| **上游变动** | 被测系统（DGM / pi）会 breaking change | 锁版本；只通过一层薄适配器接触它们 |

## 14. 与已有工作的定位关系

### 14.1 别人在做什么

- **论文线**（GEPA / ACE / DGM / SEAL）：会进化，但几乎不管记忆。扫过的 9 个仓库里，Letta / Mem0 / Zep / TencentDB-Agent-Memory 零命中。
- **记忆线**（AWM / ReasoningBank）：有记忆，但从不与进化线合流，而且也是自己造轮子。
- **产品线**（MemOS / OpenViking / EverOS / Letta / TencentDB-Agent-Memory）：记忆是绝对主流，"自进化"和"记忆"几乎是同一个词。
- **门控线**（Tracely-ai / agent-qa）：给人类开发者的 CI 工具，守人工变更，不做进化循环内的选择压力。

### 14.2 本项目的位置

> **记忆系统存内容，本项目存"能力状态 + 因果归因"。**

前者是检索问题，后者是进化选择压力问题。这是两个不同的数据结构。

明确不碰：

- 不做"又一个记忆层"（11k~47k stars 的项目已占满）
- 不做"又一个门控"（1400 stars 的项目已占满）
- 不做"又一个自进化框架"（几十个，最大的 47k stars）

## 16. 待定问题

1. **"一项能力"怎么定义？** 整个设计唯一真正难的地方。前期建议用粗粒度、人工可读的标签。
2. **provider 与预算？** 决定能跑多少代、每代几个重复样本（统计显著性需要重复）。当前 API key 未配置，是最大阻塞。
3. **被测系统选哪个？** DGM（代码层）还是 ACE（上下文层）作为第一个被测对象。
4. **主旋钮先选哪两个？** 建议准确率 + token。
